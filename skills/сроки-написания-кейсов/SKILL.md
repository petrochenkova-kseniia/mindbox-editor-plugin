# Сроки написания кейсов

## Что делает
По названию или ссылке на карточку в Trello считает четыре метрики:
1. **Бриф → публикация** — общий цикл от создания карточки. Бюджет 15 нед.
2. **Бриф окнули → публикация** — от выхода из колонки приёма брифа. Показывает рабочий цикл без ожидания заказчика. Бюджета нет, нужна для сравнения с общим циклом.
3. **В работе у автора** — с подключения автора до публикации. Бюджета нет, нужна для оценки лага между приёмом брифа и стартом работы.
4. **Чисто у автора в работе** — рабочих дней в авторских колонках, минус ожидания и встречи. Бюджет 5 нед = 25 раб. дней.

Плюс отдельная проверка — **SLA редактора по итерациям** (3 раб. дня на одну итерацию).

## Шаг 0. Перед первым запуском — проверка подключения к Trello

Trello можно использовать двумя способами. Проверь по порядку:

### Способ 1. MCP Trello (предпочтительный)

Посмотри среди доступных инструментов есть ли что-то вида `mcp__trello__*` или `mcp__*__trello-*`. Если есть — попробуй вызвать поиск карточки и получение её истории/комментариев через этот MCP. Если он умеет отдавать движения между списками (action log) и комментарии — используй его и переходи к шагу 1. Если MCP есть, но не отдаёт нужные данные (только базовое чтение карточки) — fallback на способ 2.

### Способ 2. Локальный скрипт + API key

Проверь credentials:
```bash
ls ~/Claude/integrations/credentials/trello.json
```

**Если файла нет — проведи через настройку:**

1. `mkdir -p ~/Claude/integrations/credentials`
2. Скажи пользователю буквально:
   > Чтобы скилл мог читать карточки, нужно дать доступ к Trello. Открой **https://trello.com/power-ups/admin**:
   > 1. Войди в аккаунт.
   > 2. Нажми «New», создай Power-Up с любым названием.
   > 3. В разделе «API Key» нажми «Generate a new API key» — скопируй.
   > 4. Под полем API Key открой ссылку «Token», разреши доступ, скопируй токен.
   > 5. Пришли мне обе строки.
3. Запиши через Write tool в `~/Claude/integrations/credentials/trello.json`:
   ```json
   {"api_key": "...", "token": "..."}
   ```
   **Никогда не повторяй ключи в чате.**
4. Проверь подключение: `python3 $SKILL_BASE/references/trello_helper.py boards`. Если вернулся список досок — покажи welcome-сообщение (ниже). Если 401 — ключи неверные.

(`$SKILL_BASE` — базовая директория скилла, указана в системном сообщении)

### Welcome-сообщение (показать один раз после успешной настройки)

> Подключение к Trello готово. Теперь я могу анализировать твои кейсы.
>
> **Как пользоваться.** В любом разговоре скажи: «Проанализируй кейс Купер» (название из Trello). Я найду карточку, посчитаю четыре метрики и SLA редактора, покажу разбивку по этапам. Если что-то неоднозначно — спрошу.
>
> **Можно вписать сразу в гуглодок.** Если дашь ссылку на Google Doc — оформлю результат прямо в нём (плашки + разбивка + редактор + буллеты), чтобы накапливать историю по кейсам.
>
> **Можно сделать рутину.** Рутина — это автозапуск скилла по расписанию, без твоей команды. Например, каждый понедельник в 9:00 я сам прохожусь по списку твоих активных кейсов, считаю сроки и присылаю тебе короткую сводку: где успеваешь, где впритык, где отстаёшь. Полезно, чтобы каждую неделю получать срез по всем кейсам без ручного запуска — особенно перед редколлегией. Если хочешь — скажи «настрой рутину для сроков написания кейсов», и я задам пару вопросов (какие кейсы, когда запускать).

## Шаг 1. Найди карточку

Пользователь говорит: «проанализируй кейс X» или даёт ссылку https://trello.com/c/SHORT.

```bash
python3 $SKILL_BASE/references/trello_helper.py search "X"
```

Если есть короткий ID из ссылки — можно сразу взять карточку через API.

- Несколько результатов — покажи варианты, спроси.
- Один — бери ID.
- Ничего — попроси уточнить название или ссылку.

## Шаг 2. Достань историю карточки

```bash
python3 $SKILL_BASE/references/trello_helper.py history CARD_ID
```
Получишь: дату создания и первую колонку, все перемещения с датами, все комментарии с авторами.

## Шаг 3. Посчитай метрики

### Важное общее правило для метрик 3.1–3.3 (все недельные)

Из всех трёх недельных метрик **вычитай календарные дни, когда материал зависал на клиенте** (заказчике или герое). Это колонки в Trello:
- «Герой смотрит черновик»
- «Герой смотрит чистовик»
- «Заказчик читает чистовик»
- «Заказчик комментирует»
- «Зависло на ранней стадии»
- «Зависло на поздней стадии»

**Почему:** недельные метрики показывают нагрузку на нашу сторону — на команду журнала. Если кейс висит у спикера месяц, это не наше время. Без вычета метрика искажается: длинные ожидания клиента маскируют скорость работы команды.

В разбивке по этапам клиентские колонки **показывай**, чтобы было видно, где провисло — но в плашки они не входят. В буллетах «Что пошло не по сценарию» обязательно проговори, сколько суммарно ждали клиента.

### 3.1. Бриф → публикация (общий цикл)
Старт — дата создания карточки. Конец — дата публикации или сегодня. По календарным неделям **минус дни на клиенте** (см. выше). Бюджет 15 нед.

### 3.2. Бриф окнули → публикация
Старт — первый осмысленный выход карточки из колонки приёма брифа («Заказчик принимает бриф», «Редакция принимает бриф», «Бриф») в рабочую колонку (Очередь, Герои отвечают, Автор пишет черновик). Если такой колонки нет или бриф окнули мгновенно — равна общему циклу. По календарным неделям **минус дни на клиенте**.

Длинный бриф (большой разрыв между метриками 3.1 и 3.2) — сигнал, что ждали заказчика, а не работали.

### 3.3. В работе у автора
Ищи комментарий от первого лица с любым из: «погружусь / погружаюсь», «беру / возьму / возьмусь», «подхвачу / подключаюсь», «назначаю интервью», «договорился(сь) о встрече», «начинаю писать / драфт / собирать / готовиться».

Это комментарий автора о себе, а не «возьмёт этот человек» (назначение, не подключение).

Если такого нет — первое попадание в авторскую/подготовительную колонку («автор задаёт вопросы», «автор готовит интервью», «герои отвечают на вопросы автора», «автор пишет черновик»).

По календарным неделям **минус дни на клиенте**. Если лаг от «бриф окнули» больше недели — флажь.

### 3.4. Чисто у автора в работе
Суммируй рабочие дни во всех авторских колонках. Без выходных и праздников.

**Авторские колонки** — с одним из в названии: «автор пишет», «автор дорабатывает», «автор чистовик». Остальные — не авторские.

**Вычитай:**
- День интервью с клиентом.
- День встречи с клиентом.
- День, когда редактор вернул материал (это день редактора, автор начинает со следующего).
- Дни ожидания внутри авторской колонки. Признаки ожидания в комментариях:
  - «жду цифры / материалы / встречу / клиента»
  - «клиент готовится к ивенту»
  - «спикер в отпуске / на больничном»
  - «клиент перенёс звонок»
  - «клиент не отвечает / напомнилась»
  - «после ивента / после отпуска»

  Если карточка стояла в авторской колонке долго, но в комментариях нет признаков ожидания — спроси пользователя.

**Добавляй:**
- Подготовка к интервью — 1–3 рабочих дня по факту. Оцени по комментариям между «погружусь» и днём интервью: активно собирал вопросы, делал драфт, ходил на доп-встречу — больше; просто назначил слот — 1. При сомнениях спроси.

Сравни с бюджетом 25 рабочих дней.

### 3.5. SLA редактора по итерациям (бюджет 3 раб. дня на одну итерацию)

Считай **по комментариям**, не по двигам в Trello. Карточку часто двигают с задержкой — реальная работа короче, метрика по двигам завышает картину.

**Старт итерации** — коммент автора вида: «сдаю / посмотри пожалуйста / принесла черновик / можно смотреть / зову на ревью / отдаю на ревью».

**Конец итерации** — коммент редактора вида: «прошлась / посмотрела / готово / прокомментировала / пробежалась».

**Правила подсчёта:**
- День сдачи **не** считаем (автор отдаёт обычно в середине дня).
- День ответа редактора **считаем**.
- Считаем рабочие дни между этими датами (без выходных и праздников).
- Каждую итерацию проверяй отдельно. Суммарно по всем итерациям **не** считаем — SLA на одну итерацию, а не на весь кейс.
- Если итерация не состоялась (редактор не дошёл, материал вернули обратно к спикеру/автору без коммента «посмотрела») — пропускай.

**Если хотя бы одна итерация > 3 раб. дней** — подсветить отдельным блоком, явно назвать редактора (Полина / Ксюша / другой), сказать какая итерация (черновик #N / чистовик #N), указать диапазон дат и контекст превышения (например, «коммуникационный сбой: автор не сразу прислал актуальную ссылку»).

### Праздники
По производственному календарю России на текущий год — с праздниками и переносами. Если не помнишь точные даты — через WebSearch («производственный календарь России [год]») или спроси.

## Шаг 4. Сформируй ответ

Формат — плашки сверху, потом разбивка одной строкой, отдельный блок про редактора, потом «Что пошло не по сценарию».

### Образец

> # Кейс «Название»
>
> | **9,7 нед** | **5 нед** | **4,3 нед** | **7 дней** |
> |---|---|---|---|
> | бриф → публикация | бриф окнули → публикация | в работе у автора | чисто у автора в работе |
>
> Заказчик принимает бриф 33д · Очередь 5д · Герои отвечают 7д · Автор пишет черновик 4д · Редактор 4д · Автор дорабатывает 1д · Редактор 4д · Автор дорабатывает 1д · Герой смотрит черновик 2д · Герой смотрит чистовик 2д · Пост и креатив 3д · Корректор <1д · Вёрстка 2д · Публикуем 4д.
>
> **Редактор по итерациям:** 2 раб. дня (черновик) · 2 раб. дня (чистовик). Обе в SLA.
>
> ### Что пошло не по сценарию
> - Бриф 33 дня висел на стороне заказчика.
> - Спасли марш-броском.
> - Автор сделала очень плотно — 7 раб. дней при бюджете 25.
> - Редактор уложилась в SLA в обеих итерациях.

**Правила:**
- В плашках — крупные цифры (числа метрик) и подписи мелким шрифтом.
- В разбивке — все этапы (колонки) в одну строку через ` · `, **календарные** дни. Можно подсветить жирным самые длинные.
- Блок про редактора — отдельной строкой после разбивки. Если все итерации в SLA — пишем «Все в SLA». Если есть превышение — подсвечиваем (см. 3.5) и объясняем контекст.
- «Что пошло не по сценарию» — буллеты с фактурой: главные заторы, кто тормозил, что повлияло на сроки.
- Если кейс в графике без проблем — буллетов мало (2–3), фокус на «что получилось хорошо».

Если по комментариям не получается понять, работа или ожидание — спроси. Не додумывай.

## Шаг 5. Опционально — записать результат в Google Doc

Если пользователь дал ссылку на Google Doc или просит «впиши в док / запиши в [док]» — оформи блок в том же формате прямо в документ.

**Структура блока в доке:**
1. **HEADING_2** с названием кейса, текст залинкован на карточку в Trello.
2. **Таблица 1×4** — плашки. В каждой ячейке: число метрики крупно (fontSize 20pt) + перенос строки + подпись мелким шрифтом (обычный размер).
3. **Параграф с разбивкой** по этапам (одной строкой через ` · `).
4. **Параграф «Редактор по итерациям»** с цифрами и оценкой SLA.
5. **HEADING_3** «Что пошло не по сценарию».
6. **Bullet list** с фактурой.

**Чем писать:**
- `gws docs documents batchUpdate` через CLI `gws` (Google Workspace CLI).
- Вставка идёт в конец документа (перед последним `\n`). Чтобы insertTable не падал, после H2-заголовка вставлять двойной `\n` — нужен запасной параграф для таблицы.
- Ячейки таблицы заполнять в обратном порядке (с CELL 3 к CELL 0), чтобы индексы не сдвигались.
- Списку буллетов применять `createParagraphBullets` с пресетом `BULLET_DISC_CIRCLE_SQUARE`.

Если несколько кейсов записываются подряд — каждый блок добавляется ниже предыдущего, документ накапливает историю.

## Что не делаем
- Не работаем с календарём.
- Не сохраняем результат локально — каждый раз свежие данные из Trello.
- Не создаём, не двигаем и не комментируем карточки в Trello — только читаем.
- Не используем колонки Trello для подсчёта SLA редактора — только комментарии.

## Как сделать скилл рутиной (автозапуск)

Если пользователь говорит «настрой рутину для сроков написания кейсов», «хочу сводку по понедельникам» — настрой автозапуск.

**Что уточнить:**
1. Какие кейсы (например: «Купер, Авторусь, EMKA»).
2. Когда (день недели, время; по умолчанию — пн 9:00).
3. Подробность сводки (по умолчанию — короткая таблица, см. ниже).
4. Писать ли в Google Doc (если да — какая ссылка).

**Чем создавать (в порядке приоритета):**
1. **MCP scheduled-tasks**, если подключён — `mcp__scheduled-tasks__create_scheduled_task`. Промт: «Прогони скилл сроки-написания-кейсов по кейсам [список]. Дай сводку коротко: четыре метрики, SLA редактора, вердикт. Без полной разбивки по этапам.»
2. **Скилл `schedule`** — сам проведёт через создание.
3. Иначе скажи пользователю, что нужно подключить MCP scheduled-tasks.

**В рутинном запуске** — обычный алгоритм (шаги 1–3) по каждому кейсу из списка, собрать короткую сводку:

> Сводка, понедельник 9:00
>
> | Кейс | Цикл | Автор | Редактор | Статус |
> |---|---|---|---|---|
> | Купер | 10/15 нед | 22/25 дн | в SLA | впритык ⚠️ |
> | Авторусь | 4/15 нед | 8/25 дн | в SLA | в графике |
> | EMKA | 12/15 нед | 28/25 дн | ⚠️ 5 раб. дней (чистовик) | отстаёт ⛔ |
>
> EMKA — превышен бюджет автора и SLA редактора. Если хочешь, разберу детально.
