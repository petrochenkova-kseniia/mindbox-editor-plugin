# Сроки написания кейсов

## Что делает
По названию или ссылке на карточку в Trello считает пять метрик:
1. **Бриф → публикация** — общий цикл от создания карточки. Бюджет 15 нед.
2. **Бриф окнули → публикация** — от выхода из колонки приёма брифа. Показывает рабочий цикл без ожидания заказчика. Бюджета нет, нужна для сравнения с общим циклом.
3. **В работе у автора** — с подключения автора до публикации. Бюджета нет, нужна для оценки лага между приёмом брифа и стартом работы.
4. **Чисто у автора в работе** — рабочих дней в авторских колонках, минус ожидания и встречи. Бюджет 5 нед = 25 раб. дней.
5. **Срок на клиенте** — суммарно календарных дней в клиентских колонках (герой смотрит черновик/чистовик, кейс «завис»). Бюджета нет, нужна как контекст и как фильтр.

Плюс отдельная проверка — **SLA редактора по итерациям** (3 раб. дня на одну итерацию).

## Шаг 0. Перед первым запуском — проверка подключения к Trello

Trello можно использовать двумя способами. Проверь по порядку:

### Способ 1. MCP Trello (предпочтительный)

Посмотри среди доступных инструментов есть ли что-то вида `mcp__trello__*` или `mcp__*__trello-*`. Если есть — попробуй вызвать поиск карточки и получение её истории/комментариев через этот MCP. Если он умеет отдавать движения между списками (action log) и комментарии — используй его и переходи к шагу 1. Если MCP есть, но не отдаёт нужные данные (только базовое чтение карточки) — fallback на способ 2.

### Способ 2. Локальный скрипт + API key

Проверь credentials:
```bash
ls ~/Claude/integrations/credentials/trello.json
```

**Если файла нет — проведи через настройку:**

1. `mkdir -p ~/Claude/integrations/credentials`
2. Скажи пользователю буквально:
   > Чтобы скилл мог читать карточки, нужно дать доступ к Trello. Открой **https://trello.com/power-ups/admin**:
   > 1. Войди в аккаунт.
   > 2. Нажми «New», создай Power-Up с любым названием.
   > 3. В разделе «API Key» нажми «Generate a new API key» — скопируй.
   > 4. Под полем API Key открой ссылку «Token», разреши доступ, скопируй токен.
   > 5. Пришли мне обе строки.
3. Запиши через Write tool в `~/Claude/integrations/credentials/trello.json`:
   ```json
   {"api_key": "...", "token": "..."}
   ```
   **Никогда не повторяй ключи в чате.**
4. Проверь подключение: `python3 $SKILL_BASE/references/trello_helper.py boards`. Если вернулся список досок — покажи welcome-сообщение (ниже). Если 401 — ключи неверные.

(`$SKILL_BASE` — базовая директория скилла, указана в системном сообщении)

### Welcome-сообщение (показать один раз после успешной настройки)

> Подключение к Trello готово. Теперь я могу анализировать твои кейсы.
>
> **Как пользоваться.** В любом разговоре скажи: «Проанализируй кейс Купер» (название из Trello). Я найду карточку, посчитаю пять метрик и SLA редактора, покажу разбивку по этапам. Если что-то неоднозначно — спрошу.
>
> **Можно вписать сразу в гуглодок.** Если дашь ссылку на Google Doc — оформлю результат прямо в нём (плашки + разбивка + редактор + буллеты), чтобы накапливать историю по кейсам.
>
> **Можно сделать рутину.** Рутина — это автозапуск скилла по расписанию, без твоей команды. Например, каждый понедельник в 9:00 я сам прохожусь по списку твоих активных кейсов, считаю сроки и присылаю тебе короткую сводку: где успеваешь, где впритык, где отстаёшь. Полезно, чтобы каждую неделю получать срез по всем кейсам без ручного запуска — особенно перед редколлегией. Если хочешь — скажи «настрой рутину для сроков написания кейсов», и я задам пару вопросов (какие кейсы, когда запускать).

## Шаг 1. Найди карточку

- Один — бери ID.
- Ничего — попроси уточнить название или ссылку.

```bash
python3 $SKILL_BASE/references/trello_helper.py history CARD_ID
```
Получишь: дату создания и первую колонку, все перемещения с датами, все комментарии с авторами.

## Шаг 3. Посчитай метрики

### Классификация колонок Trello

Чтобы метрики не путались, держи в голове, в какое «ведро» относится каждая колонка:

| Категория | Колонки | Куда идёт |
|---|---|---|
| **Бриф** | «Заказчик принимает бриф», «Редакция принимает бриф» | в общий цикл и 3.2 |
| **Очередь** | «Очередь», «Беклог/отложено» | в общий цикл |
| **Подготовительная** | «Герои отвечают на вопросы редактора и автора» | в общий цикл; условно в 3.4 (см. ниже) |
| **Авторские (черновик/чистовик)** | «Автор пишет черновик», «Автор дорабатывает черновик», «Автор пишет чистовик» | в 3.4 |
| **Редакторские** | «Редактор комментирует», «Редактор читает чистовик» | в общий цикл |
| **Клиентские** | «Герой смотрит черновик», «Герой смотрит чистовик», «Зависло на ранней стадии», «Зависло на поздней стадии» | в 3.5 |
| **Заказчик** (внутренний стейкхолдер Mindbox: account-менеджер / CSM) | «Заказчик читает чистовик», «Заказчик комментирует» | только в общий цикл |
| **Пост-продакшн (тоже авторские)** | «Пишем пост и задание на креатив», «Корректор вычитывает материал и пост», «Дизайн картинок», «Вёрстка», «Галочка в пайпе», «Карточка кейса для страницы клиентов» | в 3.4 |
| **Публикация** | «Публикуем в журнале и в соцсетях» | в общий цикл |

**Важно:** «Заказчик» — это **внутренний стейкхолдер от Mindbox** (account-менеджер / CSM / тот, кто привёл проект в редакцию), а **не клиент-компания**. Поэтому колонки «Заказчик читает чистовик» и «Заказчик комментирует» **не идут** в «срок на клиенте». Они учитываются только в общем цикле «бриф → публикация».

### Важное общее правило для метрик 3.1–3.3 (все недельные)

Недельные метрики считаем по **календарным неделям** — все реальные сроки работы, без вычетов. Это даёт честную картину «сколько прошло от X до Y».

Отдельно считай **срок на клиенте** (метрика 3.5) — суммарно календарных дней в клиентских колонках (см. таблицу выше). Заказчик и подготовительная — не клиент.

**Почему так:** раньше дни на клиенте вычитали из недельных метрик. Это искажало картину: получалось, что кейс «успели за 8 недель», хотя по факту прошло 13. Теперь честнее — считаем как есть, а ожидание клиента выносим отдельной плашкой, чтобы было видно, где именно прошло время.

### Правило исключения из выборки

Если **на одном клиентском этапе карточка стояла > 30 календарных дней** — кейс **исключается из статистики**. Считаем именно по одному этапу, а не сумме: суммарно >30 дней может набежать в нормальном кейсе (черновик + чистовик), а вот если один этап (например, «Герой смотрит черновик») висит больше месяца — это уже выброс.

Метрики всё равно считай и покажи, но добавь сверху явную плашку-предупреждение (см. шаг 4). Логика: такие кейсы перекошены ожиданием клиента и портят сравнение с остальными.

В сводных рутинах (понедельничная сводка) — выноси такие кейсы в отдельный блок «Исключены из выборки» в конце.

### 3.1. Бриф → публикация (общий цикл)
Старт — дата создания карточки. Конец — дата публикации или сегодня. По календарным неделям. Бюджет 15 нед.

### 3.2. Бриф окнули → публикация
Старт — первый осмысленный выход карточки из колонки приёма брифа («Заказчик принимает бриф», «Редакция принимает бриф», «Бриф») в рабочую колонку (Очередь, Герои отвечают, Автор пишет черновик). Если такой колонки нет или бриф окнули мгновенно — равна общему циклу. По календарным неделям.

Длинный бриф (большой разрыв между метриками 3.1 и 3.2) — сигнал, что ждали заказчика, а не работали.

### 3.3. В работе у автора
Ищи комментарий от первого лица с любым из: «погружусь / погружаюсь», «беру / возьму / возьмусь», «подхвачу / подключаюсь», «назначаю интервью», «договорился(сь) о встрече», «начинаю писать / драфт / собирать / готовиться».

Это комментарий автора о себе, а не «возьмёт этот человек» (назначение, не подключение).

Если такого нет — первое попадание в авторскую/подготовительную колонку («автор задаёт вопросы», «автор готовит интервью», «герои отвечают на вопросы автора», «автор пишет черновик»).

По календарным неделям. Если лаг от «бриф окнули» больше недели — флажь.

### 3.4. Чисто у автора в работе
Суммируй рабочие дни во всех авторских колонках. Без выходных и праздников.

**Авторские колонки** — это весь продакшн материала до публикации. Сюда входят:
- «Автор пишет черновик», «Автор дорабатывает черновик», «Автор пишет чистовик» — классические колонки автора
- «Пишем пост и задание на креатив» — автор пишет пост
- «Корректор вычитывает материал и пост» — короткий этап, автор отдаёт корректору и вносит правки
- «Вёрстка» — автор верстает кейс
- «Дизайн картинок» — автор взаимодействует с дизайнером
- «Галочка в пайпе» — финальные согласования по биллингу
- «Карточка кейса для страницы клиентов» — автор делает карточку клиента на сайте

**Колонка «Публикуем в журнале и в соцсетях»** — постпродакшн, в 3.4 НЕ считается. Это уже после того, как материал опубликован.

**Shadow-автор в колонке «Герои отвечают на вопросы редактора и автора».** Иногда автор пишет черновик в гуглдоке параллельно с тем, как спикер отвечает на вопросы — карточка при этом стоит в «Герои отвечают». В таком случае часть этого интервала тоже идёт в авторские.

Алгоритм определения, когда автор реально сел писать (внутри интервала «Герои отвечают»):

1. **Сначала ищем прямой маркер** «начинаю писать / пишу черновик / сажусь писать / приступаю к черновику / набрасываю драфт / формирую структуру / собираю драфт / собираю кейс» — считаем рабочие дни с даты этого коммента до конца интервала.
2. **Если прямого маркера нет** — ищем маркер сдачи: ссылка на `docs.google.com` ИЛИ комменты вида «несу черновик / сдаю / сформировала структуру / сформировала костяк / принесла черновик». Если такой маркер нашёлся, отматываем НАЗАД до коммента-обязательства автора («погружусь / возьмусь / завтра пишу / в понедельник сяду») в том же интервале — это и есть старт. Если коммента-обязательства раньше не было, считаем с начала интервала (бенефит сомнения — автор всё это время готовился к черновику).
3. **Если ни первого, ни второго маркера нет** — этап остаётся подготовительным, в авторские не идёт.

Логика такая: «Герои отвечают» по умолчанию это ожидание спикера, не автора. Засчитываем как авторский только когда видим объективные следы того, что автор писал черновик.

**Вычитай:**
- День интервью с клиентом.
- День встречи с клиентом.
- День, когда редактор вернул материал (это день редактора, автор начинает со следующего).
- **Редакторские дни ревью внутри авторских колонок.** Когда редактор ревьюит вёрстку или пост (например, в колонке «Вёрстка» Полина прошлась по верстке за 1 раб. день) — этот день учитывается в SLA редактора (см. 3.6), а не в авторских. Иначе один и тот же день будет посчитан дважды.
- Дни ожидания внутри авторской колонки. Признаки ожидания в комментариях:
  - «жду цифры / материалы / встречу / клиента»
  - «клиент готовится к ивенту»
  - «спикер в отпуске / на больничном»
  - «клиент перенёс звонок»
  - «клиент не отвечает / напомнилась»
  - «после ивента / после отпуска»
  - «жду креативы / иллюстрации / картинки / Интенсу» (характерно для колонок «Вёрстка» и «Дизайн картинок»)
  - «жду корректора»
  - «жду финальное согласование / жду спикера, чтобы опубликовать»

  Если карточка стояла в авторской колонке долго, но в комментариях нет признаков ожидания — спроси пользователя.

**Добавляй:**
- Подготовка к интервью — 1–3 рабочих дня по факту. Оцени по комментариям между «погружусь» и днём интервью: активно собирал вопросы, делал драфт, ходил на доп-встречу — больше; просто назначил слот — 1. При сомнениях спроси.

Сравни с бюджетом 25 рабочих дней.

**Про бюджет:** 25 раб. дн — исторический ориентир, заложенный под классические колонки «автор пишет / дорабатывает / чистовик». С учётом расширенного набора (вёрстка, пост, карточка кейса) бюджет может быть тесноват — отметить, если кейс плотно подошёл к 25 дням, и обсудить с командой пересмотр.

### 3.5. Срок на клиенте

Суммарно **календарных дней** во всех клиентских колонках:
- «Герой смотрит черновик»
- «Герой смотрит чистовик»
- «Зависло на ранней стадии»
- «Зависло на поздней стадии»

Это пятая плашка в таблице. Заказчик-колонки (внутренний стейкхолдер) в эту метрику НЕ идут — они показываются отдельно в разбивке.

- Если максимум по одному клиентскому этапу ≤ 30 кд — обычный показатель, выводим как есть.
- Если по любому одному этапу > 30 кд — срабатывает правило исключения из выборки. Покажи метрики, но сверху таблицы — плашка-предупреждение (см. шаг 4).

В буллетах «Что пошло не по сценарию» проговори, на каких этапах конкретно зависло (например, «28 дней — герой смотрел черновик, 12 дней — герой смотрел чистовик»).

### 3.6. SLA редактора по итерациям (бюджет 3 раб. дня на одну итерацию)

Считай **по комментариям**, не по двигам в Trello. Карточку часто двигают с задержкой — реальная работа короче, метрика по двигам завышает картину.

**Primary editors** — те, кто реально делает ревью авторских драфтов: **Полина Лукьянович** и **Ксюша Петроченкова**. Только их комменты «прошлась / посмотрела / прокомментировала» закрывают итерацию. Юля Рыбникова — редактор сайта, может в конкретном кейсе быть автором или редактором, для целей SLA не считается primary.

**Что считается итерацией.** Любое ревью редактора по любому артефакту автора:
- Черновик (классика)
- Чистовик (классика)
- Вёрстка — когда редактор смотрит свёрстанный кейс
- Пост — когда редактор смотрит пост в соцсети и для рассылки

SLA 3 раб. дня — на каждую отдельную итерацию.

**Старт итерации** — коммент автора вида: «сдаю / посмотри пожалуйста / принесла черновик / можно смотреть / зову на ревью / отдаю на ревью / несу черновик / посмотри вёрстку / посмотри пост».

**Конец итерации** — коммент primary-редактора вида: «прошлась / посмотрела / готово / прокомментировала / пробежалась / откомментировала / оставила комментарии».

**Правила подсчёта:**
- День сдачи **не** считаем (автор отдаёт обычно в середине дня).
- День ответа редактора **считаем**.
- Считаем рабочие дни между этими датами (без выходных и праздников).
- Каждую итерацию проверяй отдельно. Суммарно по всем итерациям **не** считаем — SLA на одну итерацию, а не на весь кейс.
- Если итерация не состоялась (редактор не дошёл, материал вернули обратно к спикеру/автору без коммента «посмотрела») — пропускай.

**Если хотя бы одна итерация > 3 раб. дней** — подсветить отдельным блоком, явно назвать редактора (Полина / Ксюша), сказать какая итерация (черновик #N / чистовик #N / вёрстка / пост), указать диапазон дат и контекст превышения (например, «коммуникационный сбой: автор не сразу прислал актуальную ссылку»). Если внутри итерации застряло ожидание клиента (между сдачей и ответом редактора кейс уехал на ревью к спикеру) — пометь, что это, скорее всего, ложно-положительное срабатывание, не реальное превышение SLA редактора.

### Праздники
По производственному календарю России на текущий год — с праздниками и переносами. Если не помнишь точные даты — через WebSearch («производственный календарь России [год]») или спроси.

## Шаг 4. Сформируй ответ

Формат — плашка-предупреждение (если есть), плашки сверху, потом разбивка одной строкой, отдельный блок про редактора, потом «Что пошло не по сценарию».

### Образец — обычный кейс (все клиентские этапы ≤ 30 кд)

> # Кейс «Название»
>
> | **13 нед** | **8 нед** | **7 нед** | **7 дней** | **4 дней** |
> |---|---|---|---|---|
> | бриф → публикация | бриф окнули → публикация | в работе у автора | чисто у автора в работе | срок на клиенте |
>
> Заказчик принимает бриф 33д · Очередь 5д · Герои отвечают 7д · Автор пишет черновик 4д · Редактор 4д · Автор дорабатывает 1д · Редактор 4д · Автор дорабатывает 1д · Герой смотрит черновик 2д · Герой смотрит чистовик 2д · Заказчик комментирует 5д · Пост и креатив 3д · Корректор <1д · Вёрстка 2д · Публикуем 4д.
>
> **Редактор по итерациям:** 2 раб. дня (черновик) · 2 раб. дня (чистовик) · 1 раб. день (вёрстка) · <1 раб. дня (пост). Все в SLA.
>
> ### Что пошло не по сценарию
> - Бриф 33 дня висел на стороне заказчика.
> - Срок на клиенте 4 дня (герой смотрел черновик и чистовик по 2 дня) — в норме. Заказчик дополнительно комментировал 5 дней — это внутреннее согласование, не клиент.
> - Автор сделала очень плотно — 7 раб. дней при бюджете 25.
> - Редактор уложилась в SLA в обеих итерациях.

### Образец — исключённый кейс (один этап > 30 кд)

> # Кейс «Название»
>
> > ⚠️ **Исключён из выборки.** На этапе «Герой смотрит черновик» карточка простояла 38 дней (>30 кд за один этап). Метрики показаны, но в сравнении с другими кейсами не учитываем: затор на этом этапе сильно искажает картину.
>
> | **15 нед** | **10 нед** | **9 нед** | **8 дней** | **40 дней** |
> |---|---|---|---|---|
> | бриф → публикация | бриф окнули → публикация | в работе у автора | чисто у автора в работе | срок на клиенте |
>
> Заказчик принимает бриф 10д · Очередь 3д · Герои отвечают 5д · Автор пишет черновик 5д · **Герой смотрит черновик 38д** · Редактор 3д · Автор дорабатывает 2д · Заказчик комментирует 17д · Герой смотрит чистовик 2д · Пост и креатив 3д · Вёрстка 2д · Публикуем 4д.
>
> **Редактор по итерациям:** 3 раб. дня (черновик) · 2 раб. дня (чистовик) · 1 раб. день (вёрстка). Все в SLA.
>
> ### Что пошло не по сценарию
> - 38 дней герой смотрел черновик — спикер уехал в командировку. Это и есть причина исключения из выборки.
> - 17 дней заказчик комментировал чистовик — внутреннее согласование с account-менеджером, в «срок на клиенте» не идёт.
> - При вычете клиентского времени работа команды уложилась в график.

**Правила:**
- В плашках — крупные цифры (числа метрик) и подписи мелким шрифтом. Пять плашек подряд.
- **Плашка-предупреждение** ставится сверху таблицы **только если хотя бы один клиентский этап (герой/«зависло») простоял > 30 календарных дней**. В обычных кейсах её нет. Текст плашки указывает конкретный этап и сколько дней он стоял.
- В разбивке — все этапы (колонки) в одну строку через ` · `, **календарные** дни. Можно подсветить жирным самые длинные. Колонки заказчика («Заказчик читает чистовик», «Заказчик комментирует») идут в строке как обычные этапы, но в «срок на клиенте» не суммируются.
- Блок про редактора — отдельной строкой после разбивки. Если все итерации в SLA — пишем «Все в SLA». Если есть превышение — подсвечиваем (см. 3.6) и объясняем контекст.
- «Что пошло не по сценарию» — буллеты с фактурой: главные заторы, кто тормозил, что повлияло на сроки. Если срок на клиенте большой — обязательно проговори, на каких этапах. Если в разбивке есть значительное время «Заказчик…» — отдельно отметь, что это внутреннее согласование, не клиент.
- Если кейс в графике без проблем — буллетов мало (2–3), фокус на «что получилось хорошо».

Если по комментариям не получается понять, работа или ожидание — спроси. Не додумывай.

## Шаг 5. Опционально — записать результат в Google Doc

Если пользователь дал ссылку на Google Doc или просит «впиши в док / запиши в [док]» — оформи блок в том же формате прямо в документ.

**Структура блока в доке:**
1. **HEADING_2** с названием кейса, текст залинкован на карточку в Trello.
2. **Параграф-предупреждение** (только если на одном клиентском этапе > 30 кд) — выделить жирным и/или цветом. Текст: «⚠️ Исключён из выборки. На этапе „X" карточка простояла N дней (>30 кд за один этап)».
3. **Таблица 1×5** — плашки. В каждой ячейке: число метрики крупно (fontSize 20pt) + перенос строки + подпись мелким шрифтом (обычный размер).
4. **Параграф с разбивкой** по этапам (одной строкой через ` · `).
5. **Параграф «Редактор по итерациям»** с цифрами и оценкой SLA.
6. **HEADING_3** «Что пошло не по сценарию».
7. **Bullet list** с фактурой.

**Чем писать:**
- `gws docs documents batchUpdate` через CLI `gws` (Google Workspace CLI).
- Вставка идёт в конец документа (перед последним `\n`). Чтобы insertTable не падал, после H2-заголовка (или после параграфа-предупреждения, если он есть) вставлять двойной `\n` — нужен запасной параграф для таблицы.
- Ячейки таблицы заполнять в обратном порядке (с CELL 4 к CELL 0), чтобы индексы не сдвигались.
- Списку буллетов применять `createParagraphBullets` с пресетом `BULLET_DISC_CIRCLE_SQUARE`.

Если несколько кейсов записываются подряд — каждый блок добавляется ниже предыдущего, документ накапливает историю.

## Что не делаем
- Не работаем с календарём.
- Не сохраняем результат локально — каждый раз свежие данные из Trello.
- Не создаём, не двигаем и не комментируем карточки в Trello — только читаем.
- Не используем колонки Trello для подсчёта SLA редактора — только комментарии.

## Как сделать скилл рутиной (автозапуск)

Если пользователь говорит «настрой рутину для сроков написания кейсов», «хочу сводку по понедельникам» — настрой автозапуск.

**Что уточнить:**
1. Какие кейсы (например: «Купер, Авторусь, EMKA»).
2. Когда (день недели, время; по умолчанию — пн 9:00).
3. Подробность сводки (по умолчанию — короткая таблица, см. ниже).
4. Писать ли в Google Doc (если да — какая ссылка).

**Чем создавать (в порядке приоритета):**
1. **MCP scheduled-tasks**, если подключён — `mcp__scheduled-tasks__create_scheduled_task`. Промт: «Прогони скилл сроки-написания-кейсов по кейсам [список]. Дай сводку коротко: пять метрик, SLA редактора, вердикт. Кейсы, где один клиентский этап >30 кд выноси в отдельный блок „Исключены из выборки". Без полной разбивки по этапам.»
2. **Скилл `schedule`** — сам проведёт через создание.
3. Иначе скажи пользователю, что нужно подключить MCP scheduled-tasks.

**В рутинном запуске** — обычный алгоритм (шаги 1–3) по каждому кейсу из списка, собрать короткую сводку. Кейсы, где один клиентский этап >30 кд — отдельным блоком внизу:

> Сводка, понедельник 9:00
>
> | Кейс | Цикл | Автор | Клиент | Редактор | Статус |

> | Купер | 10/15 нед | 22/25 дн | 8 дн | в SLA | впритык ⚠️ |
> | Авторусь | 4/15 нед | 8/25 дн | 5 дн | в SLA | в графике |
> | EMKA | 12/15 нед | 28/25 дн | 12 дн | ⚠️ 5 раб. дней (чистовик) | отстаёт ⛔ |

> EMKA — превышен бюджет автора и SLA редактора. Если хочешь, разберу детально.
